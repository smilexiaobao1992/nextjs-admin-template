# 电商库存管理系统设计

**日期：** 2026-07-28  
**状态：** 已获用户确认  
**基础项目：** `nextjs-admin-template`

## 1. 目标

在现有 Next.js 管理后台模板上建设一套以实体库存为核心的电商库存管理系统。系统需要统一管理货品、SKU、多仓库存、组合商品、出入库、调拨、盘点、平台交易文件导入、库存预警、统计报表和操作审计。

实体仓库存是唯一真实库存。多个电商平台共享实体库存，但允许后续为不同平台或店铺配置独立分配量和安全库存。平台订单仅作为出库或退货的来源凭证，不建设完整订单履约系统。

## 2. 成功标准

- 用户可以维护和批量导入货品、SKU，并查看可定位到仓库和库位的库存。
- 所有库存变化均来自已入账业务单据，并能追溯到库存流水和操作人。
- 组合商品出库能按配置自动拆分并扣减基础 SKU。
- 平台文件导入不会因重复文件、重复明细或未匹配 SKU 造成错误库存。
- 系统能展示各平台和店铺的出库、退货及销量统计。
- 系统能发现低库存、缺货、积压和异常库存。
- 关键操作具有不可由普通用户修改或删除的审计记录。

## 3. 范围边界

### 3.1 包含

- 货品、SKU、分类、单位、条码和启停状态
- Excel/CSV 货品批量导入及错误报告
- 组合商品及基础 SKU 用量配置
- 多仓库和库位
- 入库、出库、退货入库、调拨、库存调整和盘点
- 库存余额和不可变库存流水
- 平台、店铺、平台 SKU 与内部 SKU 映射
- 平台已发货订单及退款退货文件导入
- 安全库存、缺货、积压和异常库存预警
- 库存、出入库、平台销量、退货、库龄和周转统计
- 动态角色权限、菜单和操作审计

### 3.2 不包含

- 平台实时 API 对接
- 付款、审单、客服、收件地址、面单、物流发货等完整 OMS 能力
- 采购合同、供应商结算和财务核算
- 自动向平台回写可售库存
- 移动端扫码仓储作业
- 高级需求预测或自动采购决策

这些能力如后续确认需要，应在当前库存账本上增量建设，不改变库存真值来源。

## 4. 交付拆分

系统按依赖关系拆成三个实施阶段。每个阶段独立验收，后续阶段只通过已定义的领域接口使用库存能力。

### 阶段一：库存核心

- 货品、SKU、分类、单位和批量导入
- 仓库、库位和默认仓设置
- 组合商品及 BOM
- 入库、出库、调拨、调整和盘点单
- 库存余额、库存流水和并发保护
- 库存工作台和基础查询
- 权限、菜单和操作审计

### 阶段二：平台交易流水

- 平台和店铺
- 平台 SKU 映射
- 可扩展文件解析器
- 已发货订单导入并生成销售出库
- 退款退货导入并生成退货入库
- 重复检测、待匹配区和异常处理

### 阶段三：预警和统计

- SKU/仓库安全库存及渠道分配配置
- 低库存、缺货、积压和异常库存预警
- 库存、出入库、平台销量和退货统计
- 库龄、周转率和基于明确规则的补货建议

## 5. 技术架构

继续使用现有单体全栈架构：Next.js 16 App Router、React 19、TypeScript、PostgreSQL、Drizzle ORM、Better Auth 和动态 RBAC。不新增微服务或新数据库。

遵循模板的“路由薄、feature 厚、UI 纯、auth/db 共享”边界：

- `src/app/app/<route>` 负责会话、权限检查、查询调用和页面组装。
- `src/features/<domain>` 负责领域查询、Server Action、校验和业务组件。
- `src/lib/<domain>` 负责库存过账、导入解析、审计等可独立测试的领域服务。
- `src/lib/db/schema.ts` 统一导出数据库 schema；按阶段生成并审查迁移。
- 所有业务写操作在服务端重新校验权限，不以菜单可见性代替授权。

领域边界如下：

- `catalog`：货品、SKU、分类、单位、组合商品
- `warehouses`：仓库、库位
- `inventory`：单据、过账、余额、流水、盘点
- `channels`：平台、店铺、SKU 映射
- `imports`：上传、解析、暂存、校验、确认
- `alerts`：预警规则及当前预警
- `analytics`：只读统计查询
- `audit`：追加式操作事件

## 6. 核心数据模型

以下名称为概念模型，实施计划可根据现有命名约定调整，但不能改变约束。

### 6.1 货品和组合商品

- `product`：货品 SPU、名称、分类、品牌、状态、备注
- `sku`：内部唯一 SKU 编码、货品、规格名称、条码、单位、状态
- `bundle_component`：组合 SKU、基础 SKU、正数用量

阶段一不支持组合商品嵌套。组合 SKU 不能直接成为另一个组合 SKU 的组件，避免循环和多层换算歧义。

### 6.2 仓库和库存

- `warehouse`：唯一编码、名称、状态、是否默认仓
- `warehouse_location`：所属仓库、库位编码、名称、状态；仓库内编码唯一
- `inventory_balance`：SKU、仓库、库位、当前数量、版本号和更新时间
- `stock_document`：单号、类型、状态、来源、来源编号、业务日期、备注和创建人
- `stock_document_line`：单据、SKU、数量、源/目标仓库与库位
- `stock_movement`：单据行、SKU、仓库、库位、带符号数量、变动后余额和时间

数量使用支持小数的定点类型，不使用浮点数。余额表服务于高频查询，库存流水是审计和重建余额的依据。

### 6.3 平台和导入

- `sales_channel`：淘宝/天猫、京东、拼多多、抖音、快手、微信小店、亚马逊、线下等平台
- `channel_store`：平台下的具体店铺
- `channel_sku_mapping`：店铺、平台商品/规格编码、内部 SKU
- `import_job`：业务类型、平台、店铺、文件名、文件哈希、状态、统计和操作人
- `import_row`：原始行、规范化数据、匹配结果、校验错误和处理状态
- `channel_transaction`：平台订单号、明细号、业务类型、SKU、数量、业务时间和来源导入批次

平台交易唯一键至少覆盖“平台、店铺、订单号、明细号、业务类型”，并结合文件哈希防止重复导入。

### 6.4 预警和审计

- `inventory_policy`：SKU、仓库、安全库存、目标库存、积压天数等规则
- `audit_event`：操作人、动作、对象类型、对象 ID、修改前后数据、IP、User-Agent、请求 ID、导入批次、结果和时间

审计事件只允许追加和查询。应用不提供更新或删除入口。

## 7. 库存不变量和单据状态

库存单据状态为：

- `draft`：可编辑，不影响库存
- `posted`：已入账，内容不可修改，已生成库存流水
- `reversed`：通过独立反向单据完整回冲原流水

业务规则：

1. 页面和通用 CRUD 不得直接修改库存余额。
2. 过账必须在单个数据库事务中完成单据校验、余额锁定、负库存检查、流水写入、余额更新和审计记录。
3. 默认禁止负库存。余额不足时整张单据过账失败，不产生部分流水。
4. 多行过账按稳定的 SKU/仓库/库位顺序锁定余额，降低死锁概率。
5. 调拨同时生成源仓负向流水和目标仓正向流水，两侧必须在同一事务中成功。
6. 盘点单记录账面数量、实盘数量和差异；入账时只对差异生成流水。
7. 已入账单据不能直接编辑或删除。纠错通过有来源关联的反向单据完成。
8. 禁用中的 SKU、仓库或库位不能用于新单据，但历史记录必须可查。

## 8. 组合商品规则

- 组合 SKU 是销售和映射层对象，不单独持有实体库存。
- 保存单据草稿时可展示组合结构；过账时将组合数量乘以组件用量，聚合为基础 SKU 数量。
- 过账单据保存当时使用的组件快照，后续修改 BOM 不改变历史出库。
- 任一组件库存不足时，整张单据过账失败并返回具体缺货组件。
- 组合商品可售数量按所有组件可支持数量的最小值计算。

## 9. 用户流程

### 9.1 货品导入

1. 下载固定模板或上传受支持的 Excel/CSV。
2. 系统创建导入批次，解析为暂存行。
3. 校验必填字段、SKU 唯一性、条码冲突、单位及关联值。
4. 用户查看成功、警告、错误和重复行，可下载错误报告。
5. 用户明确排除错误行或修正后确认。
6. 确认在事务中写入货品/SKU，并记录导入批次和审计事件。

### 9.2 库存单据

1. 有创建权限的用户新建草稿并添加明细。
2. 页面展示预计库存影响和缺货提示。
3. 有过账权限的用户二次确认。
4. 服务端在事务中完成过账；成功后跳转只读详情和流水。
5. 纠错时创建反向单据，保留原单、反向单和操作人关联。

### 9.3 平台文件导入

1. 用户选择平台、店铺和业务类型后上传平台导出文件。
2. 对应解析器将平台列名转换为统一交易结构。
3. 系统检查文件哈希、交易唯一键和历史批次。
4. 平台 SKU 通过已保存映射关联内部 SKU；未匹配行进入待处理区。
5. 用户确认映射，系统重新校验全部待导入行。
6. 已发货交易生成销售出库草稿，实际退回交易生成退货入库草稿。
7. 具有过账权限的用户确认单据后才影响库存。

平台文件导入不占用待发货库存，也不承担实时防超卖。渠道安全库存用于降低人工导入滞后的风险。

## 10. 页面和菜单

- 工作台：库存总览、待办、预警和近期出入库
- 货品管理：货品、SKU、组合商品、分类、单位、批量导入
- 仓库管理：仓库、库位
- 库存管理：库存查询、流水、入库、出库、调拨、调整、盘点
- 平台管理：平台、店铺、SKU 映射
- 导入中心：上传、批次、错误、待匹配和结果
- 预警中心：低库存、缺货、积压和异常
- 统计分析：库存、出入库、销量、退货、库龄、周转
- 系统管理：用户、角色、权限、菜单、操作日志

列表提供分页、搜索和必要筛选。库存明细可从“余额 → 流水 → 来源单据 → 导入批次”逐层追溯。

## 11. 权限设计

沿用动态 RBAC，新增最小必要权限键：

- 货品：查看、维护、导入
- 仓库：查看、维护
- 库存：查看、创建单据、过账、冲销、盘点
- 平台：查看、维护映射、导入
- 预警和统计：查看、导出
- 审计：查看

创建草稿与过账分权。所有 Server Action 和页面服务端入口重新调用权限校验。

## 12. 操作审计

以下操作必须生成审计事件：

- 货品、SKU、BOM、仓库、库位和映射的新增、修改、启停
- 单据创建、修改、过账和冲销
- 文件上传、确认导入、排除错误行和映射修改
- 预警规则修改和报表导出
- 用户、角色、权限和菜单变更
- 登录相关的安全事件在现有认证能力允许的边界内记录

审计数据包含关键修改前后值，不记录密码、会话令牌、数据库连接串等秘密。

## 13. 错误处理和一致性

- 表单验证失败返回字段级中文提示，不执行数据库写入。
- 库存过账使用全有或全无事务；失败后保留草稿和原因。
- 导入解析只写暂存区，不直接改变库存。
- 导入确认前重新读取映射和余额，避免使用过期预览结果。
- 同一导入批次重复确认必须返回既有结果，不重复创建业务单据。
- 未匹配 SKU、重复交易和格式错误分别展示，不以通用“导入失败”隐藏来源。
- 报表只读取已入账流水；草稿和失败导入不计入统计。
- 数据库错误写入服务端日志；客户端只显示可处理的信息，不暴露 SQL 或秘密。

## 14. 性能和安全

- 高频筛选字段建立复合索引，包括 SKU/仓库/库位、单据状态/日期、平台/店铺/业务时间和审计对象/时间。
- 列表和流水使用服务端分页，不一次加载完整历史。
- 余额查询读取 `inventory_balance`，统计和追溯读取 `stock_movement`。
- 文件类型、大小、行数和解析耗时设置上限；公式按普通文本处理，不执行上传内容。
- 导出和审计查看均要求服务端权限。
- 第一阶段不引入缓存；只有真实性能数据证明需要时再增加。

### 15.3 阶段一验收场景

1. 批量导入基础 SKU 和一个组合 SKU。
2. 向默认仓入库基础 SKU。
3. 出库组合 SKU，确认基础 SKU 按 BOM 扣减。
4. 尝试超量出库，确认整单失败且余额不变。
5. 调拨到第二仓并完成盘点差异。
6. 冲销一张已入账单据并追溯双向流水。
7. 以无过账权限角色尝试过账并确认被拒绝。
8. 在操作日志中查看上述关键操作及前后数据。

## 16. 已确认的产品决策

- 实体仓库存为唯一真实库存，平台共享库存。
- 数据模型从第一天支持多仓，第一期可仅启用默认仓。
- 支持组合商品及多个基础 SKU 搭配。
- 所有主流平台和线下渠道纳入平台模型，但文件解析器按实际样本逐个实现。
- 无平台 API 时通过人工下载文件和导入中心关联 SKU。
- 第一版不建设完整订单管理，只保留轻量平台交易来源。
- 操作审计是核心能力，不视为可选增强。
- 默认禁止负库存，纠错使用反向流水。
