# 电商库存管理系统设计

**日期：** 2026-07-28

**状态：** 已获用户确认

**基础项目：** `nextjs-admin-template` 只读模板

**新项目目录：** `/Users/xujunbao/WebstormProjects/claude/ecommerce-inventory`

## 1. 目标

在现有 Next.js 管理后台模板上建设一套以实体库存为核心的电商库存管理系统。系统需要统一管理货品、SKU、多仓库存、组合商品、出入库、调拨、盘点、平台交易文件导入、库存预警、统计报表和操作审计。

实施时复制模板的受版本控制业务文件到当前工作目录下的新项目 `ecommerce-inventory`，不在 `nextjs-admin-template` 模板仓库内开发业务功能。复制时排除 `.git`、`node_modules`、`.next`、本地环境变量和构建产物，新项目使用自己的 Git 历史和环境配置。

实体仓库存是唯一真实库存。多个电商平台共享实体库存，但允许后续为不同平台或店铺配置独立分配量和安全库存。平台订单仅作为出库或退货的来源凭证，不建设完整订单履约系统。

## 2. 成功标准

- 用户可以维护和批量导入货品、SKU，为货品上传主图，并查看可定位到仓库和库位的库存。
- 登录成功后首先进入真实数据驱动的库存仪表盘，不显示模板演示数据。
- 所有库存变化均来自已入账业务单据，并能追溯到库存流水和操作人。
- 组合商品出库能按配置自动拆分并扣减基础 SKU。
- 平台文件导入不会因重复文件、重复明细或未匹配 SKU 造成错误库存。
- 系统能展示各平台和店铺的出库、退货及销量统计。
- 系统能按明确口径发现低库存、缺货、滞销和异常库存。
- 关键操作具有不可由普通用户修改或删除的审计记录。

## 3. 范围边界

### 3.1 包含

- 货品、SKU、分类、单位、条码、主图和启停状态
- Excel/CSV 货品批量导入及错误报告
- 组合商品及基础 SKU 用量配置
- 多仓库和库位
- 入库、出库、退货入库、调拨、库存调整和盘点
- 库存余额和不可变库存流水
- 平台、店铺、平台 SKU 与内部 SKU 映射
- 平台已发货订单及退款退货文件导入
- 安全库存、缺货、超目标库存、滞销和异常库存预警
- 库存、出入库、平台销量、退货和周转统计
- 动态角色权限、菜单和操作审计

### 3.2 不包含

- 平台实时 API 对接
- 付款、审单、客服、收件地址、面单、物流发货等完整 OMS 能力
- 采购合同、供应商结算和财务核算
- 自动向平台回写可售库存
- 移动端扫码仓储作业
- 高级需求预测或自动采购决策

这些能力如后续确认需要，应在当前库存账本上增量建设，不改变库存真值来源。

## 4. 交付拆分

系统按依赖关系拆成三个实施阶段。每个阶段独立验收，后续阶段只通过已定义的领域接口使用库存能力。

### 阶段一：库存核心

- 货品、SKU、分类、单位、主图和批量导入
- 仓库、库位和默认仓设置
- 组合商品及 BOM
- 入库、出库、调拨、调整和盘点单
- 库存余额、库存流水和并发保护
- 登录后默认库存仪表盘和基础查询
- 权限、菜单和操作审计

### 阶段二：平台交易流水

- 平台和店铺
- 平台 SKU 映射
- 所有渠道均可使用的标准交易模板（CSV/XLSX）
- 可扩展原生平台文件解析器；每个平台在取得真实导出样本后单独验收
- 已发货订单导入并生成销售出库
- 退款退货导入并生成退货入库
- 重复检测、待匹配区和异常处理

### 阶段三：预警和统计

- SKU/仓库安全库存及渠道展示策略
- 低库存、缺货、超目标库存、滞销和异常库存预警
- 库存、出入库、平台销量和退货统计
- 周转率和基于目标库存的补货缺口

## 5. 技术架构

继续使用现有单体全栈架构：Next.js 16 App Router、React 19、TypeScript、PostgreSQL、Drizzle ORM、Better Auth 和动态 RBAC。不新增微服务或新数据库。

货品图片复用 `kailex/web` 已验证的 Supabase Storage 服务端上传模式，引入官方 `@supabase/supabase-js` 客户端，仅在服务端使用 service role。数据库保存对象路径而不是图片二进制或易漂移的完整公开 URL。

`nextjs-admin-template` 仅作为复制来源。所有业务 schema、迁移、页面、测试和提交都写入新项目 `ecommerce-inventory`；模板仓库保留为可复用基线，不承载库存业务代码。

遵循模板的“路由薄、feature 厚、UI 纯、auth/db 共享”边界：

- `src/app/app/<route>` 负责会话、权限检查、查询调用和页面组装。
- `src/features/<domain>` 负责领域查询、Server Action、校验和业务组件。
- `src/lib/<domain>` 负责库存过账、导入解析、审计等可独立测试的领域服务。
- `src/lib/db/schema.ts` 统一导出数据库 schema；按阶段生成并审查迁移。
- 所有业务写操作在服务端重新校验权限，不以菜单可见性代替授权。

领域边界如下：

- `catalog`：货品、SKU、分类、单位、组合商品
- `warehouses`：仓库、库位
- `inventory`：单据、过账、余额、流水、盘点
- `channels`：平台、店铺、SKU 映射
- `imports`：上传、解析、暂存、校验、确认
- `alerts`：预警规则及当前预警
- `analytics`：只读统计查询
- `audit`：追加式操作事件

## 6. 核心数据模型

以下名称为概念模型，实施计划可根据现有命名约定调整，但不能改变约束。

### 6.1 货品和组合商品

- `product`：货品 SPU、名称、分类、品牌、主图对象路径、主图替代文本、状态、备注
- `sku`：内部唯一 SKU 编码、货品、规格名称、条码、单位、状态
- `bundle_component`：组合 SKU、基础 SKU、正数用量

阶段一不支持组合商品嵌套。组合 SKU 不能直接成为另一个组合 SKU 的组件，避免循环和多层换算歧义。
每个 SKU 只有一个库存基础单位，阶段一不做箱、件等单位换算。所有数量使用 `numeric(18,4)`，业务校验要求数量精度不超过四位小数。

### 6.1.1 货品图片

- 阶段一每个货品支持一张主图，不建设图库、裁剪器或 AI 图片处理。
- 支持 JPG、PNG、WebP，单张最大 2MB；客户端用于即时提示，服务端重新校验 MIME、大小和扩展名。
- 对象存储 bucket 通过环境变量配置，默认可沿用 `inventory-images`，对象统一写入 `ecommerce-inventory/products/<uuid>.<ext>`，避免与旧系统路径冲突。
- 数据库存储对象路径，展示时通过当前 Supabase URL 和 bucket 解析公开 URL；service role 永不发送到浏览器。
- 上传需要货品维护权限。新文件上传后若货品保存失败，系统清理新对象；替换成功后才删除旧对象，避免数据库指向不存在的图片。
- 删除货品主图同时清空数据库路径并删除本系统前缀下的对象；不允许删除前缀以外的存储对象。
- 未配置存储时，货品其他字段仍可保存，图片区域显示明确配置错误，不回退为数据库 Base64。
- 货品列表显示小尺寸缩略图，详情/编辑显示预览，并为图片提供基于货品名称的替代文本。

### 6.2 仓库和库存

- `warehouse`：唯一编码、名称、状态、是否默认仓
- `warehouse_location`：所属仓库、库位编码、名称、状态；仓库内编码唯一
- `inventory_balance`：SKU、仓库、库位、当前数量、版本号和更新时间
- `stock_document`：单号、类型、状态、来源、来源编号、业务日期、备注和创建人
- `stock_document_line`：单据、SKU、数量、源/目标仓库与库位
- `stock_document_component`：组合商品过账时使用的基础 SKU、用量和快照
- `stock_movement`：单据行、SKU、仓库、库位、带符号数量、变动后余额和时间

库存始终落到库位，不允许 `NULL` 库位。创建仓库时自动创建不可删除的 `DEFAULT` 默认库位，暂不细分库位的用户也通过该库位记账。`inventory_balance` 的唯一键为 SKU、仓库、库位。

系统初始化时创建一个默认仓。任一时刻必须且只能有一个启用中的默认仓；数据库部分唯一索引保证最多一个，领域服务阻止停用或删除最后一个启用中的默认仓。

余额表服务于高频查询，库存流水是审计和重建余额的依据。

### 6.3 平台和导入

- `sales_channel`：淘宝/天猫、京东、拼多多、抖音、快手、微信小店、亚马逊、线下等平台
- `channel_store`：平台下的具体店铺
- `channel_sku_mapping`：店铺、平台商品/规格编码、内部 SKU
- `import_job`：业务类型、平台、店铺、文件名、文件哈希、状态、统计和操作人
- `import_row`：原始行、规范化数据、匹配结果、校验错误和处理状态
- `channel_transaction`：外部业务事件号、平台订单号、明细号、规范化业务类型、SKU、数量、业务时间和来源导入批次

平台交易唯一键为“平台、店铺、业务类型、外部业务事件号”，并结合文件哈希防止重复导入。发货事件号可使用平台稳定的发货明细号；退货必须使用退款/售后单号或其他稳定退货事件号。同一订单明细发生多次部分退货时，每次退货必须有不同事件号。没有稳定事件号的原生文件不能直接入账，需先在暂存区补充唯一事件号。

阶段二首先交付所有平台通用的标准模板。必填列为：业务事件号、订单号、明细号、平台 SKU、数量、业务时间；平台、店铺和业务类型由上传页面选择。一个文件只能对应一种业务类型，文件内不再提供业务类型列，避免两个来源冲突。业务类型只接受：

- `shipped`：平台已发货，可生成销售出库草稿
- `returned_received`：仓库确认实物已退回，可生成退货入库草稿

仅退款、退款申请、退款完成但实物未收回等状态不改变库存，也不属于标准库存模板的导入范围。部分退货数量不得超过该订单明细的已发货数量减去历史已入库退货数量。

淘宝/天猫、京东、拼多多、抖音、快手、微信小店、亚马逊和线下渠道均可使用标准模板。直接读取某个平台原生导出文件属于取得样本后的条件性交付项，不是阶段二完成条件：实施前必须取得该平台当前真实匿名样本，并书面确定列名、状态映射、业务事件唯一键和部分退货字段；缺少样本时不猜测平台格式，也不阻塞标准模板交付。

### 6.4 预警和审计

- `inventory_policy`：SKU、仓库、安全库存、目标库存、滞销天数等规则
- `channel_inventory_policy`：店铺、SKU、仓库、展示上限和渠道安全缓冲
- `audit_event`：操作人、动作、对象类型、对象 ID、修改前后数据、IP、User-Agent、请求 ID、导入批次、结果和时间

审计事件只允许追加和查询。应用不提供更新或删除入口。

`channel_inventory_policy` 不预占实体库存，也不进入库存账本。在无实时 API 的阶段，它只计算建议平台展示量：`max(0, min(展示上限, 实体库存 - 仓库安全库存 - 渠道安全缓冲))`；展示上限为空时只应用安全缓冲。多个平台仍共享同一实体库存，因此该建议不能承诺实时防超卖，页面必须明确提示人工导入存在时差。硬预留和自动回写不属于当前范围。

## 7. 库存不变量和单据状态

库存单据状态为：

- `draft`：可编辑，不影响库存
- `posted`：已入账，内容不可修改，已生成库存流水
- `reversed`：原单已被一张独立且已入账的反向单据完整回冲

业务规则：

1. 页面和通用 CRUD 不得直接修改库存余额。
2. 过账必须在单个数据库事务中完成单据校验、余额锁定、负库存检查、流水写入、余额更新和审计记录。
3. 默认禁止负库存。余额不足时整张单据过账失败，不产生部分流水。
4. 多行过账按稳定的 SKU/仓库/库位顺序锁定余额，降低死锁概率。
5. 调拨同时生成源仓负向流水和目标仓正向流水，两侧必须在同一事务中成功。
6. 盘点单记录账面数量、实盘数量和差异；入账时只对差异生成流水。
7. 已入账单据不能直接编辑或删除。纠错通过系统根据原流水生成的 `reversal` 类型反向单据完成；反向单据本身状态为 `posted`，不允许人工编辑。
8. 禁用中的 SKU、仓库或库位不能用于新单据，但历史记录必须可查。
9. 原单从 `posted` 变为 `reversed` 与反向单据过账必须在同一事务中完成。`reversal_of_document_id` 具有唯一约束，每张原单只能完整冲销一次，反向单据不能再次冲销。
10. 报表按全部已入账流水的带符号数量求和；原流水与反向流水自然抵消。`reversed` 只表示原单已回冲，不从流水查询中额外排除原单。

### 7.1 单据行为矩阵

| 类型 | 必填位置 | 库存影响 | 可录入组合 SKU | 额外规则 |
| --- | --- | --- | --- | --- |
| 普通/采购入库 | 目标仓库和库位 | 目标位置增加 | 否 | 只录入基础 SKU |
| 销售/普通出库 | 源仓库和库位 | 源位置减少 | 是 | 组合 SKU 按快照拆成基础 SKU |
| 退货入库 | 目标仓库和库位 | 目标位置增加 | 否 | 只按实际收回的基础 SKU；组合销售退货必须人工确认实际收回组件 |
| 调拨 | 不同的源和目标仓库/库位 | 源减少、目标增加 | 否 | 两侧在同一事务中过账 |
| 库存调整 | 一个仓库和库位 | 正数增加或负数减少 | 否 | 非零带符号数量且必须填写原因 |
| 盘点 | 一个仓库和库位 | 按实盘数与账面数之差调整 | 否 | 实盘数不得小于零 |
| 反向单据 | 从原单继承 | 完整镜像原流水 | 系统生成 | 不允许人工新建或编辑 |

## 8. 组合商品规则

- 组合 SKU 是销售和映射层对象，不单独持有实体库存。
- 保存单据草稿时可展示组合结构；过账时将组合数量乘以组件用量，聚合为基础 SKU 数量。
- 过账单据保存当时使用的组件快照，后续修改 BOM 不改变历史出库。
- 任一组件库存不足时，整张单据过账失败并返回具体缺货组件。
- 组合商品可售数量按所有组件可支持数量的最小值计算。
- 平台退货行映射到组合 SKU 时，系统用原销售出库的组件快照创建“待确认组件”退货草稿，但不自动增加库存。仓库人员必须勾选并填写实际收回的基础 SKU 数量；全部组件完整退回时可以一键应用原快照，缺件或部分退回时按实物调整。确认后的退货入库行仍只包含基础 SKU。

## 9. 用户流程

### 9.1 货品导入

1. 下载固定模板或上传受支持的 Excel/CSV。
2. 系统创建导入批次，解析为暂存行。
3. 校验必填字段、SKU 唯一性、条码冲突、单位及关联值。
4. 用户查看成功、警告、错误和重复行，可下载错误报告。
5. 用户明确排除错误行或修正后确认。
6. 确认在事务中写入货品/SKU，并记录导入批次和审计事件。

### 9.2 库存单据

1. 有创建权限的用户新建草稿并添加明细。
2. 页面展示预计库存影响和缺货提示。
3. 有过账权限的用户二次确认。
4. 服务端在事务中完成过账；成功后跳转只读详情和流水。
5. 纠错时创建反向单据，保留原单、反向单和操作人关联。

### 9.3 平台文件导入

1. 用户选择平台、店铺和单一业务类型后上传平台导出文件。
2. 对应解析器将平台列名转换为统一交易结构。
3. 系统检查文件哈希、交易唯一键和历史批次。
4. 平台 SKU 通过已保存映射关联内部 SKU；未匹配行进入待处理区。
5. 用户确认映射，系统重新校验全部待导入行。
6. `shipped` 交易生成销售出库草稿；只有 `returned_received` 交易可生成退货入库草稿。组合 SKU 退货草稿必须先确认实际收回组件。
7. 具有过账权限的用户确认单据后才影响库存。

平台文件导入不占用待发货库存，也不承担实时防超卖。渠道安全库存用于降低人工导入滞后的风险。

- 货品管理：货品、主图、SKU、组合商品、分类、单位、批量导入
- 仓库管理：仓库、库位
- 库存管理：库存查询、流水、入库、出库、调拨、调整、盘点
- 平台管理：平台、店铺、SKU 映射
- 导入中心：上传、批次、错误、待匹配和结果
- 预警中心：低库存、缺货、超目标库存、滞销和异常
- 统计分析：库存、出入库、销量、退货和周转
- 系统管理：用户、角色、权限、菜单、操作日志

所有业务列表必须提供搜索、必要筛选、排序、分页、空状态和错误状态，不允许一次读取整表后在浏览器内过滤。查询条件写入 URL，刷新、返回和复制链接后保持一致。库存明细可从“余额 → 流水 → 来源单据 → 导入批次”逐层追溯。

### 10.1 统一列表规范

- 货品、SKU、组合商品、仓库、单据、平台、店铺、映射、导入批次和预警使用服务端页码分页。
- 默认每页 20 条，可选择 20、50、100 条，服务端硬限制单页最多 100 条。
- 搜索至少覆盖业务名称和主编码；SKU 列表同时支持 SKU、条码和货品名称。
- 筛选项按页面提供状态、仓库、单据类型、平台、店铺和时间范围等必要条件。
- 默认排序必须稳定，在业务排序字段相同时追加主键排序，避免翻页时重复或遗漏。
- 库存流水和操作日志只允许按时间正序或倒序，按 `(created_at, id)` 使用与方向一致的游标分页，避免大偏移量分页随数据增长退化；其他字段只用于搜索和筛选，不作为排序项。界面仍提供上一页、下一页和每页数量。
- 查询函数只选择列表实际展示的字段，关联数据批量查询或通过明确 join 获取，禁止逐行查询造成 N+1。
- 搜索、筛选、排序和分页都在 PostgreSQL 中执行；客户端只负责提交查询条件和渲染结果。
- 每个列表提供加载中、无结果、查询失败和无权限的明确状态。

### 10.2 仪表盘

仪表盘从第一阶段开始交付，所有数字均来自数据库查询，不保留模板演示值。第一阶段展示：

- 货品 SPU 数量
- SKU 数量，其中组合 SKU 单独标识
- 有库存的 SKU 数量、仓库数量，以及按基础单位分组的实体库存数量（例如“件”“千克”分别展示，禁止跨单位相加）
- 各仓库存量分布
- 草稿单据和待过账单据数量
- 最近库存流水和最近操作日志

第二阶段在同一仪表盘增加：

- 各平台店铺数量
- 各平台已映射商品/SKU 数量
- 可选择时间范围的平台发货数量和实退数量
- 待匹配平台 SKU、失败导入和待确认批次数量
- 平台数据为空时显示明确空状态及“去导入/去映射”入口，不填充假数据

第三阶段增加低库存、缺货、超目标库存、滞销、异常库存、周转率和补货缺口卡片。统计卡必须能跳转到已应用相同筛选条件的明细页。

### 10.3 UI 和操作体验

沿用模板现有设计语言、响应式后台壳、Radix UI 和 Tailwind 样式变量，不另建一套视觉系统。界面默认简体中文，目标是仓库和运营人员无需培训即可完成常用操作。

- 每个页面只有一个清晰主操作，例如“新建入库单”或“上传文件”；低频操作收进次级菜单。
- 页面结构保持一致：标题和说明、主操作、搜索筛选、结果区、分页；不在不同模块随意改变位置。
- 常用筛选直接展示，低频筛选放入“更多筛选”，并提供一键重置。
- 表格保持必要列数，长内容截断后可查看完整值；状态使用文字和颜色共同表达，不只依赖颜色。
- 新建和编辑表单按业务分组，提供合理默认仓和默认库位；字段错误显示在字段附近，保留用户已输入内容。
- 单据过账、冲销、批量导入确认等高影响操作使用明确确认界面，展示将受影响的 SKU、数量和仓库，不使用含糊的“确定吗”。
- 保存、上传、解析、过账和导出均显示进行中状态并阻止重复提交；成功后给出可追溯结果入口。
- 批量导入采用“上传 → 校验 → 修正/排除 → 确认 → 结果”步骤式流程，任何阶段都能看见当前状态和错误数量。
- 空页面提供下一步入口，例如“导入第一个货品”“创建默认仓”；不展示无意义的空图表。
- 仪表盘优先呈现需要行动的信息，卡片数量保持克制；详细分析进入对应页面。
- 桌面端优先满足高密度表格操作，同时保证手机端能查看仪表盘、列表和详情；复杂单据编辑不承诺手机端高效录入。
- 保留键盘焦点、表单标签、对话框焦点管理和足够对比度，延续 Radix UI 的无障碍能力。
- 删除、停用、过账和冲销之后不得只依赖短暂 toast；页面内同步展示最新状态和可追溯链接。

## 11. 权限设计

沿用动态 RBAC，新增最小必要权限键：

- 货品：查看、维护、导入
- 仓库：查看、维护
- 库存：查看、创建单据、过账、冲销、盘点
- 平台：查看、维护映射、导入
- 预警和统计：查看、导出
- 审计：查看

创建草稿与过账分权。所有 Server Action 和页面服务端入口重新调用权限校验。

## 12. 操作审计

以下操作必须生成审计事件：

- 货品、SKU、BOM、仓库、库位和映射的新增、修改、启停
- 货品主图上传、替换和删除；审计只记录对象路径，不记录文件内容或 service role
- 单据创建、修改、过账和冲销
- 文件上传、确认导入、排除错误行和映射修改
- 预警规则修改和报表导出
- 用户、角色、权限和菜单变更
- 登录相关的安全事件在现有认证能力允许的边界内记录

审计数据包含关键修改前后值，不记录密码、会话令牌、数据库连接串等秘密。

## 13. 错误处理和一致性

- 表单验证失败返回字段级中文提示，不执行数据库写入。
- 库存过账使用全有或全无事务；失败后保留草稿和原因。
- 导入解析只写暂存区，不直接改变库存。
- 导入确认前重新读取映射和余额，避免使用过期预览结果。
- 同一导入批次重复确认必须返回既有结果，不重复创建业务单据。
- 未匹配 SKU、重复交易和格式错误分别展示，不以通用“导入失败”隐藏来源。
- 报表只读取已入账流水；草稿和失败导入不计入统计。
- 数据库错误写入服务端日志；客户端只显示可处理的信息，不暴露 SQL 或秘密。

## 14. 性能和安全

- 高频筛选字段建立复合索引，包括 SKU/仓库/库位、单据状态/业务日期、平台/店铺/业务时间、导入状态/时间和审计对象/时间。
- 唯一业务编码使用唯一索引；组合索引顺序必须与实际查询中的等值条件、范围条件和排序一致。
- 货品和 SKU 名称先使用受分页保护的数据库搜索；只有真实性能数据证明普通搜索不足时，才引入 PostgreSQL trigram 或全文索引。
- 所有列表、流水和导出使用服务端查询，不一次加载完整历史；普通页面单次返回不超过 100 行。
- 余额查询读取 `inventory_balance`，统计和追溯读取 `stock_movement`。
- 仪表盘聚合查询相互独立时并行执行，但不为一个卡片逐行补查关联数据。
- 仪表盘和报表查询设置明确时间范围；阶段一不做无边界的全历史明细聚合。
- 大文件在导入暂存区分批解析和校验，确认库存影响时仍使用单个业务事务，避免部分过账。
- 文件类型、大小、行数和解析耗时设置上限；公式按普通文本处理，不执行上传内容。
- 图片上传同时校验 MIME、扩展名和 2MB 上限；对象路径必须限制在 `ecommerce-inventory/products/` 前缀。
- 导出和审计查看均要求服务端权限。
- 第一阶段不引入缓存；只有真实性能数据证明需要时再增加。
- 实施中对关键列表运行 `EXPLAIN` 或等价查询计划检查，确认索引被使用且不存在明显全表扫描；数据量小导致优化器合理选择顺序扫描时记录原因，不为了“出现索引”强制提示。

### 14.1 预警和统计口径

- 低库存：启用中的 SKU/仓库余额大于零且小于或等于安全库存。
- 缺货：启用中的 SKU/仓库余额等于零。负库存被业务规则禁止；若迁移或人工数据库操作产生负数，则归为异常。
- 超目标库存：设置了目标库存且当前余额大于目标库存。
- 滞销：当前余额大于零，并且在配置的滞销天数内没有销售出库负向流水；默认 90 天，可按 SKU/仓库覆盖。
- 异常库存：余额与全部已入账流水汇总不一致、禁用 SKU/仓库仍有非零余额，或出现负数余额。
- 平台销量：期间内来源为平台 `shipped` 的销售出库数量，按平台、店铺和 SKU 汇总。
- 退货量：期间内来源为 `returned_received` 的退货入库数量。
- 周转率：期间销售出库数量 ÷ 平均库存；平均库存使用 `(期初余额 + 期末余额) / 2`，期初余额由期末余额减去期间净流水反推。平均库存为零时不计算比率。
- 补货缺口：`max(0, 目标库存 - 当前余额)`，仅为明确规则的提示，不自动创建采购单。

当前范围不计算真实库龄。准确库龄需要批次或 FIFO 库存层，待明确业务需要后单独设计，不能用“最后入库时间”冒充库龄。

### 15.3 阶段一验收场景

1. 从新项目登录并确认首先进入 `/app` 库存仪表盘，页面没有模板演示数据。
2. 批量导入基础 SKU 和一个组合 SKU，确认仪表盘货品和 SKU 数量更新。
3. 为货品上传、替换和删除主图，确认列表缩略图、详情预览、存储清理和操作日志正确。
4. 向默认仓入库基础 SKU，确认库存总量、仓库分布和近期流水更新。
5. 出库组合 SKU，确认基础 SKU 按 BOM 扣减。
6. 尝试超量出库，确认整单失败且余额不变。
7. 调拨到第二仓并完成盘点差异。
8. 冲销一张已入账单据并追溯双向流水。
9. 以无过账权限角色尝试过账并确认被拒绝。
10. 在操作日志中查看上述关键操作及前后数据。

### 15.4 阶段二验收场景

1. 为八类电商平台和线下渠道创建平台/店铺记录，并使用同一标准模板导入。
2. 导入包含基础 SKU、组合 SKU、重复交易和未匹配 SKU 的 `shipped` 文件。
3. 确认重复行不生成单据，未匹配行停留在待处理区，合法行生成销售出库草稿。
4. 再次确认同一批次，确认返回既有结果且不重复创建草稿。
5. 导入 `returned_received` 和部分退货，确认累计退货不超过原发货数量。
6. 如已取得真实匿名平台样本，则按该平台适配器的独立验收清单验证；没有样本时以所有渠道可用的标准模板作为阶段完成条件。

### 15.5 阶段三验收场景

1. 配置仓库安全库存、目标库存、滞销天数和店铺展示策略。
2. 构造低库存、缺货、超目标库存、滞销和余额不一致场景，确认分类正确。
3. 核对指定期间的销售出库、退货、期初/期末库存和周转率公式。
4. 确认渠道建议展示量不修改实体余额，也不被描述为实时防超卖保证。
5. 核对补货缺口只读取目标库存和当前余额，不创建采购单据。

## 16. 已确认的产品决策

- 实体仓库存为唯一真实库存，平台共享库存。
- 数据模型从第一天支持多仓，第一期可仅启用默认仓。
- 支持组合商品及多个基础 SKU 搭配。
- 所有主流平台和线下渠道纳入平台模型并支持标准模板；原生文件解析器按真实样本逐个实现。
- 无平台 API 时通过人工下载文件和导入中心关联 SKU。
- 第一版不建设完整订单管理，只保留轻量平台交易来源。
- 操作审计是核心能力，不视为可选增强。
- 默认禁止负库存，纠错使用反向流水。
- 库存业务在当前目录下的新项目 `ecommerce-inventory` 开发，原模板仓库不承载业务修改。
- 登录后首页就是库存仪表盘，并按阶段展示货品、SKU、仓库、库存、平台和预警统计的真实数据。
- 货品支持一张主图，复用 Supabase Storage 服务端上传模式并只在数据库保存对象路径。
